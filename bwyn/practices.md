## Extreme Programming practices

Non-negotiable. The team MUST practise every one of them.

### Stories (non-negotiable)

Work is told in small stories that are easy to iterate on and test, giving a fast feedback loop. A story is small enough for a pair to finish in one iteration, and what does not fit becomes a follow-up story.

**In BWYN:** Every story starts from acceptance criteria written as Given/When/Then, and the builder drafts the smallest valuable slice and lists the rest as follow-up stories.

### Continuous integration (non-negotiable)

Changes are integrated and the full test suite is run many times a day, so integration problems show up within hours and not at the end.

**In BWYN:** A change merges only when the build passes. Changes reach the main branch through pull requests.

### Ten-Minute Build (non-negotiable)

The full build and tests finish in about ten minutes. Regressions beyond that are fixed before new feature work.

**In BWYN:** The ten-minute budget is one of the gates a change has to pass before it merges.

### Pair programming (non-negotiable)

Two people work on the code together. In BWYN, the AI depends on the human for review and feedback on each iteration.

**In BWYN:** The AI proposes and the human decides: a drafted story, enabler or ADR is only kept when the human approves it, and nothing is accepted without that review.

### Incremental design (non-negotiable)

Design grows in small steps, iteratively, as the stories need it, not all upfront.

**In BWYN:** Architecture grows through ADRs and the architectural enablers that implement them, added when a story needs them and not before.

### Single code base (non-negotiable)

One code base for the system, with no long-lived forks or copies.

**In BWYN:** The drivers, stories, enablers, ADRs and diagrams of a project live in one repository.

### Code review (non-negotiable)

Every pull request is reviewed before it is merged, to check that it follows the principles and practices of the team.

**In BWYN:** Syncing opens pull requests, so every change has a place to be reviewed before it reaches the main branch.

_Not a classic XP practice, but it is kept here among the Extreme Programming practices of the team._

## Evolutionary architecture practices

Applied through ADRs and architectural enablers. Architectural fitness functions are non-negotiable.

### Build the skeleton first

Implement a vertical slice of real functionality that crosses all the technical tiers, instead of building horizontal layers in isolation, such as finishing the whole database schema before anything uses it. A thin end-to-end slice proves the architecture works and exposes the surprises early, while they are cheap.

**In BWYN:** Architectural enablers put the skeleton in place and stories are built on it. The reference slice of the dependency injection enabler (port, use case, adapter, view model and view) proves the wiring end to end.

### Include automation early

Set up the automated build, the deployment scripts and the continuous integration pipeline from day one, before there is much to build. Automation that arrives late is paid for with manual work, and with defects that a pipeline would have caught.

**In BWYN:** The build, the type check and the test run were put in place as a Maven module by the first enabler, before any story was built on it.

### Use architectural fitness functions (non-negotiable)

Write automated, objective checks into the build pipeline, inspired by evolutionary computing, that measure whether the architecture still has the qualities it must keep: coupling limits, latency caps, security compliance. They guide change safely, because a change that breaks an architectural property fails the build.

**In BWYN:** ArchUnit rules encode the module, layer and dependency constraints of the backend (ADR 0005). A change merges only when all fitness functions pass. Frontend rules need their own ADR and enabler.

_Architectural fitness functions MUST encode the architectural constraints and run in the build._

### Defer reversible decisions

Postpone major framework and infrastructure choices until the last responsible moment, so that flexibility is kept while requirements are still moving. Decide early only what is costly to change, and learn before committing to the rest.

**In BWYN:** A decision is recorded as an ADR when it is needed. One that proves wrong is replaced by a new ADR that supersedes it, and a change to the technology stack needs an ADR.

### Grow incrementally

Expand the skeleton by adding features one at a time, keeping the system continuously executable and deployed. At every step there is a working system, never a pile of unfinished parts that only work together at the end.

**In BWYN:** Each story adds one slice on top of the skeleton, and the architecture changes only through the ADRs and enablers that a story needs. The database changes through small, incremental Flyway migrations.

### Design for testability

Write automated tests into the skeleton, so that structural changes can be verified immediately instead of feared. Code that is easy to test is also easier to change: dependencies are visible and can be substituted.

**In BWYN:** Dependencies are injected and depend on abstractions, so use cases and view models can be tested with substitutes. Acceptance criteria are automated as BDD tests with mocked adapters, and adapters have integration tests against real infrastructure.

_BDD acceptance tests and integration tests are required. Isolated unit tests are not._

### Align teams with Conway's law

Structure the development teams to mirror the architecture they must produce, so that the communication paths of the teams match the boundaries of the modules and bottlenecks do not appear between them. An organisation tends to build systems that copy its own structure, so the structure is chosen on purpose.

**In BWYN:** The system is a modular monolith whose modules expose only explicit public APIs, so a module can be owned by one team without reaching into the internals of another.
