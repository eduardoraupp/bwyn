Extreme Programming practices

Non-negotiable. The team MUST practise every one of them.

  1. 1 Stories Extreme Programming Non-negotiable

    Work is told in small stories that are easy to iterate on and test, giving a fast feedback loop. A story is small enough for a pair to finish in one iteration, and what does not fit is left out of it.

    In BWYN: Every story starts from acceptance criteria written as Given/When/Then, and the builder drafts the smallest valuable slice and names what it leaves out under Out of scope.

  2. 2 Continuous integration Extreme Programming Non-negotiable

    Changes are integrated and the full test suite is run many times a day, so integration problems show up within hours and not at the end.

    In BWYN: A change merges only when the build passes. Changes reach the main branch through pull requests.

  3. 3 Ten-Minute Build Extreme Programming Non-negotiable

    The full build and tests finish in about ten minutes. Regressions beyond that are fixed before new feature work.

    In BWYN: The ten-minute budget is one of the gates a change has to pass before it merges.

  4. 4 Pair programming Extreme Programming Non-negotiable

    Two people work on the code together. In BWYN, the AI depends on the human for review and feedback on each iteration.

    In BWYN: The AI proposes and the human decides: a drafted story, enabler or ADR is only kept when the human approves it, and nothing is accepted without that review.

  5. 5 Incremental design Extreme Programming Non-negotiable

    Design grows in small steps, iteratively, as the stories need it, not all upfront.

    In BWYN: Architecture grows through ADRs and the architectural enablers that implement them, added when a story needs them and not before.

  6. 6 Single code base Extreme Programming Non-negotiable

    One code base for the system, with no long-lived forks or copies.

    In BWYN: The drivers, stories, enablers, ADRs and diagrams of a project live in one repository.

  7. 7 Code review Extreme Programming Non-negotiable

    Every pull request is reviewed before it is merged, to check that it follows the principles and practices of the team.

    In BWYN: Syncing opens pull requests, so every change has a place to be reviewed before it reaches the main branch.

    Not a classic XP practice, but it is kept here among the Extreme Programming practices of the team.

Evolutionary architecture practices

Applied through ADRs and architectural enablers. Architectural fitness functions are non-negotiable.

  1. 1 Build the skeleton first Evolutionary architecture

    Implement a vertical slice of real functionality that crosses all the technical tiers, instead of building horizontal layers in isolation. A thin end-to-end slice proves the architecture works and exposes the surprises early, while they are cheap.

    In BWYN: Architectural enablers put the skeleton in place and stories are built on it.

  2. 2 Use architectural fitness functions Evolutionary architecture Non-negotiable

    Write automated, objective checks into the build pipeline that measure whether the architecture still has the qualities it must keep. They guide change safely, because a change that breaks an architectural property fails the build.

    In BWYN: ArchUnit rules encode the module, layer and dependency constraints of the backend. A change merges only when all fitness functions pass.

    Architectural fitness functions MUST encode the architectural constraints and run in the build.

  3. 3 Grow incrementally Evolutionary architecture

    Expand the skeleton by adding features one at a time, keeping the system continuously executable and deployed. At every step there is a working system, never a pile of unfinished parts that only work together at the end.

    In BWYN: Each story adds one slice on top of the skeleton, and the architecture changes only through the ADRs and enablers that a story needs.
